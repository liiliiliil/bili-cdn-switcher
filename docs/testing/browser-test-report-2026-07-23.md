# Bili CDN Switcher 实测报告（公开匿名版）

- 测试日期：2026-07-23
- 测试网络：澳大利亚境内的海外访问线路
- 测试浏览器：Chromium 桌面浏览器
- 测试版本：v1.5.0–v1.7.1

## 隐私处理

本公开报告刻意移除了所有测试视频 ID、标题、UP 主、个人空间、账号标识、精确播放量、完整媒体 URL、签名参数和可反查测试对象的来源页面。

样本仅以 A、B、C 等代号表示。保留的 CDN host、分辨率、缓冲状态和聚合测速结果只用于解释扩展行为。

## 结论

- 扩展只在受支持的 B 站点播页建立标签页级规则，并能观测原始 `bilivideo.com` host、运行两阶段 Range 测速、切换 host 和记录自动恢复。
- 首轮三个样本中，短时测速第一名有两次在真实播放中随后失速；扩展均切换到下一候选并恢复。这说明“有限测速 + 真实播放反馈”比永久相信一次测速可靠。
- v1.5.2 回归覆盖五条不同长度的 4K 样本。随机跳到未缓存位置后，全部恢复为 `readyState=4`，自动恢复次数为 0，没有发生误切。
- v1.6.0 回归覆盖一个既有样本、两个低热度长视频样本和两个动态页高分辨率样本。五条均成功播放并完成未缓存位置跳转，自动恢复次数为 0。
- v1.7.0-rc.1 回归确认三档自动复测设置可切换、跨扩展重载持久化并即时同步诊断；收紧权限后标签页级重定向仍正常生效。
- v1.7.0 发布包回归确认最终名称、版本、图标和 Service Worker 正常加载；点播页仍能观测媒体 host 并保持会话规则 active。
- v1.7.1 回归复现并修复了“自动结果硬过期、旧规则仍生效、内存候选为空”时无法恢复的状态。
- 同一 CDN 在一轮测试中可以跨视频稳定复用，但不同测试时段的最优 host 会变化，不应把任何单一 host 写成永久最佳答案。

## 测试方法

1. 在高画质档开始播放，等待扩展捕获当前媒体 host、有效媒体 URL 和 Range。
2. 对最多 8 个候选各读取不超过 128 KB 初筛。
3. 对前三名使用相邻的另一段 Range，各读取不超过 1 MB，复测持续吞吐。
4. 继续真实播放并观察 `readyState`、前向缓冲、当前目标和自动恢复计数。
5. 使用播放器可见进度条跳到尚未缓存的位置，确认播放器请求新的 Range 并重新建立缓冲。

每轮理论测速流量上限约 4 MB。结果只代表当时网络、路由、签发 URL 和 CDN 缓存状态。

## v1.5.1–v1.5.2 修复

### 追踪参数导致状态误重置

旧实现使用完整页面 URL 判断是否切换内容。尾斜杠或追踪参数变化可能被误判为新页面，清空当前观测状态。

修复后：

- 忽略尾斜杠、片段和普通追踪参数；
- 保留分 P、CID 和番剧身份等会改变实际播放内容的参数；
- 真正切换播放内容时仍会重置状态。

### 跳转后可能漏掉恢复检查

单纯监听 `waiting` / `stalled` 可能错过很早发生的缓冲事件，也可能被 `seeked` 的时序抵消。

v1.5.2 因此在 `play`、`seeking`、`seeked`、`waiting` 和 `stalled` 后统一安排延迟确认，并在最终确认时检查页面可见性、暂停状态、`readyState` 和前向缓冲。

五条随机跳转样本在约 6 秒后的采样点均恢复为 `readyState=4`，没有额外切换。

## 自动复测策略

- 90 分钟前：`fresh`，直接复用；
- 90 分钟后：`stale`，等待安全活动窗口；
- 2 小时后：`expired`，仍只在真实播放活动中复测；
- 页面必须可见、视频正在播放并已开始；
- 已有目标时要求至少 10 秒前向缓冲；
- 必须恰好发生真实媒体 Range 请求；
- 多标签页只允许一个自动测速任务；
- Manifest 不申请 `alarms` 权限。

本轮没有等待 90 分钟执行真实墙钟复测。时间边界、活动门槛和权限边界由自动测试覆盖；真实浏览器回归验证的是 v1.6.0 重载、播放、跨视频复用和跳转没有退化。

## v1.7.1 过期规则与卡顿恢复回归

- 使用一个公开的长时 4K 点播样本复现：自动结果为 `expired`、会话重定向仍指向旧 host、内存测速列表为空，播放器前向缓冲降为 0。
- 手动重新优选后 8 个候选中 7 个成功，页面恢复 3840×2160 播放。
- 随机跳转到约 3 分钟处后，首选节点短暂停顿；自动恢复切到下一成功候选，`recoveryCount` 从 0 增至 1。
- 恢复后的 `readyState` 为 4，前向缓冲约 9 秒，播放时间继续增长。
- 修复后，当硬过期规则仍在生效时会先释放旧规则；若没有可用内存候选，则回到 B 站原始签发节点并启动一轮新的有上限测速。
- 浏览器回归进一步确认：回退与重新测速能完成，但新规则建立后还需再次轻推播放器，才能让已失败的 MediaSource 立即发出新请求；0.15 秒不足以稳定跨过播放器的 seek 容差，v1.7.1 改为只在恢复时回退 1 秒。
- 第二轮远距离随机跳转发现，恢复 seek 会在 15 秒卡顿冷却期内触发复查；旧逻辑直接丢弃这次检查，之后不再重试。v1.7.1 改为预约冷却结束后的复查，页面一旦恢复播放则由 `playing` / `canplay` 事件取消预约。
- 冷却修复后的真实回归中，恢复计数能从 0 连续推进到 6；第 6 个候选重新建立了 3840×2160、`readyState=4` 的播放，证明恢复链不会再停在冷却期。
- 再次远距离随机跳转后，候选能够继续轮换并在耗尽时第二次回到原始节点；极弱线路下也观察到“重新测速后过早选回刚失速节点”的循环倾向。最终实现因此只在当前标签页保留最近 3 个失速 host，下一轮优先尝试其他候选；手动重新优选仍会清空这份短期记忆。
- 加入短期记忆并重新加载扩展后，最终回归在同一条匿名 3840×2160 长视频上连续执行两次远距离未缓存跳转。第一次经原始节点重新测速后，在第 3 次恢复建立约 14 秒缓冲；第二次只切换 1 个候选便恢复，继续观察时保持 `readyState=4` 和约 9–12 秒前向缓冲。
- 两次最终跳转中，恢复计数从 0 连续增长到 4，没有再次出现冷却死链，也没有在重新测速后立刻选回刚失速的节点。
- 延长观察后，第二次跳转恢复出的缓冲仍然耗尽；恢复计数继续增长，说明恢复链本身仍在运行。播放器画面显示实际下载一度只有约 0–48 KB/s，而弹窗中两个已降权候选的 1 MB 持续复测仍显示约 195 Mbps 和 262 Mbps。
- 这个量级差异说明普通媒体样本可能由更轻的音频轨或不同缓存路径主导，不能可靠代表当前 4K 视频轨。v1.7.1 最终候选因此进一步区分播放接口里的视频与音频 URL，优先用播放器实际请求的视频轨路径和对应 Range 测速；找不到视频轨时才保留原有后备路径。
- 重新加载视频轨候选后，同一位置的结果变为：两个通用候选持续复测约 11 Mbps 与 16 Mbps，另一个约 7 Mbps，其余约 0.5 Mbps、超时或失败。这个结果与真实 4K 缓冲耗尽一致，不再出现上百 Mbps 的误判。
- 将画质切为 1920×1080 做对照后，连续约 35 秒保持 `readyState=4`，前向缓冲稳定在约 30 秒，恢复计数不再增加。这说明该时段的剩余问题是所有候选都不足以稳定承担当前 4K，而不是恢复链失效。
- 新的视频轨测速使用新的内部结果版本；从旧版升级时不会继续复用旧采样结果。

测试记录不包含视频 ID、账号标识、签名 URL 或可反查的播放参数。

## v1.8.1 低缓冲趋势预警回归

本轮使用一个匿名 3840×2160 长视频，在独立标签页中把恢复计数从 0 开始观察。

- 正常播放约 40 秒时，前向缓冲在约 26–29 秒间按分片节奏回补，目标 host 未变化，恢复计数保持为 0；
- 单元测试覆盖持续下降、正常分片锯齿、起播低缓冲、拖动时间跳跃、暂停、后台和缓冲耗尽等边界，全量静态检查与 43 项测试通过；
- 压力位置起播后，缓冲先回补至约 24 秒，随后连续下降；
- 当前向缓冲还剩约 6.8 秒时，播放器仍为 `readyState=4`，恢复计数已经从 0 增至 1，证明这次切换发生在真正无缓冲之前；
- 第一次恢复后当前时段的其余候选仍不足以稳定承担 4K，既有硬卡顿兜底继续轮换；最终第 3 个候选把缓冲从约 1.5 秒增长到 15.3 秒并恢复连续播放；
- 结果说明趋势预警缩短了第一次可预见卡顿的反应时间，但不会凭空增加所有 CDN 的可用带宽；候选整体不足时仍可能需要后续恢复，降低清晰度仍是有效兜底。

趋势判断每 2 秒读取一次本地播放器状态，只在页面可见、正在播放、缓冲低于 8 秒、最近至少 8 秒持续下降且没有明显回补时生效。暂停、切到后台或拖动进度条会清空样本。记录不包含视频 ID、账号标识、标题、签名 URL或完整播放参数。

## v1.8.2–v1.8.4 连续恢复节流回归

本轮继续使用匿名 3840×2160 长视频，分别选择健康位置和未缓存压力位置，按 0.5 秒间隔记录播放器状态。

- 健康位置连续播放约 35 秒，前向缓冲从约 8 秒增长到 30 秒以上，目标未变化、恢复计数保持为 0，说明更快的明确卡顿确认没有干扰正常 4K 分片回补。
- v1.8.2 在压力位置暴露出相反方向的问题：取消跨 host 的完整 15 秒冷却后，同一次未解决的等待事件会追着新规则继续上报，恢复计数一度累计到 21，并把尚未获得充分起播时间的候选过早标成卡顿。
- v1.8.3 在内容脚本加入 7 秒换线保护，但实测仍观察到恢复计数在约 1 秒内连续增长。原因是多个恢复消息可能已经并发进入后台，单靠页面定时器不能充当权威互斥锁。
- v1.8.4 在 Service Worker 增加每标签页单飞锁和 7 秒最短换线间隔；内容脚本若收到后台冷却响应，会在剩余时间后重新确认，而不是丢掉恢复链。
- 同一压力位置的最终回归中，已完整观测到的连续换线间隔约为 9.9、15.2、10.0 和 9.9 秒；没有再次出现 1 秒内连跳。15.2 秒对应同一候选再次报告，符合原有同 host 15 秒冷却。
- 第 3 个候选曾短暂恢复 `readyState=4`，但缓冲再次耗尽；第 6 个候选重新建立播放后，继续观察约 42 秒保持 `readyState=4`，恢复计数不再增长，前向缓冲峰值约 40 秒。
- 全量语法、Manifest、权限边界、候选选择和恢复逻辑检查共 45 项通过。

结果说明这一时段确有多个候选不足以稳定承担 4K，并非每次卡顿都能靠一次换线解决；但 v1.8.4 已把“快速退出坏节点”和“不给同一次事件误杀整列候选”之间的节奏收敛到可控范围。记录省略视频 ID、标题、账号标识和签名参数。

## 用户侧确认方法

1. 播放点播视频数秒，打开扩展并确认底部版本号。
2. 确认“当前观测”和“重定向到”显示的是 `bilivideo.com` 子域名。
3. 点击“重新优选”，查看初筛和持续复测结果。
4. 继续播放；若确认发生真实无缓冲，自动恢复次数应增加并轮换目标。
5. 跳到尚未缓存的位置，确认播放器重新建立缓冲。
6. 添加或移除普通追踪参数不应清空同一播放内容的观测状态。
7. 禁用一个非原始候选，确认历史成绩仍在但它不再参选；重新启用后不应强制改动当前目标。
